# Cheshire Today Post-release QA Report — 29 July 2026

## Executive summary

This audit reviewed the current `full-scrape-prod` repository at
`2bcdf5c6571d2092d4d9294979695f5a83f8e99e` and the live production service at
`https://cheshiretoday.co.uk`. It was intentionally read-only: no production
record, scheduler, subscriber, social account or deployment state was changed.

The public site is online and usable. Health checks pass, the current frontend
bundle is being served, public article visibility is correctly filtered in the
sampled API data, key pages render responsively, crawlers receive article and
newsletter-specific metadata, both sitemaps are valid XML, the complete frontend
suite passes, focused backend security/editorial/newsletter/social suites pass,
and a production frontend build completes.

The branch is **not ready for an unconditional release sign-off**. The audit
found one critical credential exposure, an overly broad credentialed CORS
policy, unsafe production-coupled legacy tests, three tracked Python modules
with syntax errors, and several medium-severity accessibility, metadata and
performance issues. The live site can continue normal public operation, but the
Admin credential must be rotated immediately and no further release should be
approved until the critical and high-priority repository/security findings have
been corrected and retested.

## Findings by severity

### Critical

#### QA-SEC-001 — Admin credential committed in legacy tests

**Evidence:** three tracked test files contained a hard-coded Admin username and
password:

- `tests/test_facebook_features.py`;
- `tests/test_most_read_push_features.py`;
- `tests/test_scheduler_lock.py`.

The same credential also appeared in `memory/PRD.md` and five historical JSON
test reports under `test_reports/`, for nine tracked current-tree occurrences in
total at the start of containment.

The password is deliberately not reproduced here. The tests also contain live
login and state-changing requests. Because the value is present in current Git
content and history, it must be treated as compromised whether or not it is
still active.

**Impact:** unauthorized Admin access if the credential remains valid; unsafe
test execution against production; secret-scanning and repository-distribution
risk.

**Immediate action:** rotate/revoke the corresponding production Admin
credential before any other release action. Then remove all embedded credentials,
replace them with explicit test-only fixtures and ensure live mutation tests are
opt-in and cannot target production by default. Removing the string without
rotation is insufficient because Git history retains it.

**Containment status, 29 July 2026:** the pending uncommitted remediation removes
all nine current-tree occurrences, replaces the three test literals with a
loopback-only test credential helper, and adds credential-hygiene regression
coverage. A safe rescan finds zero current tracked occurrences. The value remains
in reachable Git history from the initial Render commit, and production rotation
cannot be verified from repository state. Manual rotation remains required.

### High

#### QA-TEST-001 — Backend suite is non-hermetic and includes production mutations

The unqualified backend suite cannot be safely run as a normal release gate.
One test module aborts collection unless `REACT_APP_BACKEND_URL` is supplied;
multiple legacy modules then issue direct `requests` calls for Admin login,
article-view writes, push subscriptions, newsletter preference/comment writes,
scheduler-lock operations and social posting endpoints.

With the single immediately dangerous module excluded and no external base URL,
the broad run reached `1,635 passed`, but also produced `21 failed` and `12
errors`; these failures were dominated by legacy tests trying to call relative
or external URLs rather than the in-process application. Supplying the production
URL would make those tests mutation-capable and was intentionally not done.

**Impact:** misleading CI status, accidental production writes, dependency on
credentials/network state, and inability to use the full suite as a safe release
gate.

**Recommended fix:** separate hermetic unit/ASGI tests from explicitly named
external smoke tests; fail closed when the target is production; remove embedded
credentials; require an explicit opt-in environment gate for any write-capable
external test; document the safe default command.

#### QA-CODE-001 — Three tracked Python modules do not compile

Repository-wide compilation fails with `IndentationError` in:

- `backend/config.py:14–17`;
- `backend/services/article_service.py:19–25`;
- `backend/services/auth_service.py:18–22`.

These appear to be legacy/dead modules rather than the production `server.py`
path, which compiles successfully. They have nevertheless been tracked in this
state since February 2026.

**Impact:** repository-wide Python validation fails; future imports or refactors
can activate broken code; maintainers cannot rely on compilation as a clean
release gate.

**Recommended fix:** either repair and cover the modules if they remain part of
the supported architecture, or remove them with proof that no runtime/import
contract depends on them.

#### QA-SEC-002 — Credentialed CORS accepts arbitrary origins

`backend/server.py:17644–17649` configures `allow_origins=["*"]`,
`allow_credentials=True`, all methods and all headers. A production preflight
from `https://evil.example` to a protected Admin endpoint returned `200` and:

```text
access-control-allow-origin: https://evil.example
access-control-allow-credentials: true
access-control-allow-headers: authorization,content-type
access-control-allow-methods: DELETE, GET, HEAD, OPTIONS, PATCH, POST, PUT
```

Admin authentication still requires a token, so this finding is not evidence
that an anonymous attacker can directly mutate records. It unnecessarily
removes the browser origin boundary around authenticated APIs, however, and was
already described as a post-deployment hardening item in the December 2025
deployment report.

**Recommended fix:** allow only the canonical production origin and explicit
local development origins from a validated configuration; add positive and
negative CORS regression tests for protected routes.

### Medium

#### QA-A11Y-001 — Desktop header search is not keyboard accessible

In `frontend/src/components/NewsHeader.jsx:176–211`, desktop results are clickable
`div` elements without link/button semantics, keyboard handlers or focusability.
Both desktop and mobile search inputs rely on placeholder text rather than a
programmatic label. Empty results produce no visible or live-region “no results”
state. The mobile result items are buttons and are better behaved.

Live checks confirmed that valid search terms return correct results, but Enter
does not select or submit a desktop result and a no-match query gives no feedback.

**Recommended fix:** use real links or buttons, add an accessible search label,
keyboard selection and a polite loading/no-results status. Preserve current
public filtering and canonical article URLs.

#### QA-SEO-001 — Browser DOM retains duplicate generic and page-specific metadata

The static shell defines generic homepage canonical, description and Open Graph
tags in `frontend/public/index.html:7,55–75`. Article and newsletter pages add
their own correct Helmet tags. After client rendering, the DOM contains both
sets rather than replacing the generic set:

- article: two canonicals, two descriptions, two `og:url` and two `og:image`
  values;
- newsletter: homepage and newsletter canonicals/`og:url` values together.

Crawler-specific server responses were correct for the sampled article and
newsletter page, so this is not a confirmed Google/social crawler indexing
failure. It can still confuse browser extensions, client-side sharing code,
auditing tools and nonstandard crawlers that choose the first tag.

**Recommended fix:** establish one ownership model for head metadata and add a
rendered-DOM regression asserting exactly one canonical, description and Open
Graph URL/image for each supported public route.

#### QA-SEO-002 — Unauthenticated Admin login has no `noindex`

The live `/admin` HTML and unauthenticated React login state expose the generic
homepage title/canonical and no robots meta. `AdminDashboard.jsx:2831–2835` adds
`noindex` only after authentication when the Dashboard renders. The wildcard
robots group disallows `/admin`, but the later Googlebot-specific group allows
`/` and does not repeat that disallow; bot-specific groups do not inherit the
wildcard group.

**Recommended fix:** serve `/admin` with a server-level `noindex, nofollow,
noarchive` response from the first byte, and align Googlebot rules. This is an
SEO/privacy-hygiene issue rather than proof of Admin data exposure.

#### QA-PERF-001 — Public article-list TTFB is consistently high

Production timings for `/api/articles?limit=30&with_total=true` were approximately
`1.44–1.49 s` TTFB on three warm repeat requests; an initial 100-item request
took approximately `2.93 s`. In mobile browser QA, the homepage skeleton was
visible for several seconds before content settled. The endpoint performs a
count plus multiple separately sorted article queries and applies in-process
interleaving/deduplication.

**Recommended fix:** profile Mongo execution plans and Render/database latency;
verify compound indexes for public visibility, source type and date ordering;
consider a bounded cache for the actual homepage envelope. Do not change the
40/40/20 or editorial selection logic as a performance shortcut.

#### QA-OPS-001 — Render memory risk remains only partially evidenced

Historical state records a confirmed 512 MB OOM during a 2,000-recipient Daily
Brief on 22 May and intermittent generation-time OOMs in July. Mitigations now
present include a 1,000-recipient send cap, scheduler locks, planned cursor
records, one Uvicorn worker and RSS concurrency bounded to eight.

Current code still materializes up to 15,000 subscriber records for Daily Brief
and Weekly Roundup, and Weekly Roundup can additionally materialize up to 50,000
analytics rows. RSS results remain in memory until each bounded batch gather is
assembled. This is evidence of transient peak-memory exposure, not evidence of
a leak. The social generator is bounded, in-memory and non-persistent and shows
no obvious server-side leak path.

No Render dashboard logs or metrics were available during this audit, so recent
OOM frequency and exact job correlation remain unverified. See the Render
checklist below.

## Performance and memory assessment

### Current architecture

- Render runs `render_build.sh`, which performs `npm ci`, a clean React build,
  removes `backend/frontend_build` and copies the fresh bundle there.
- Uvicorn serves `backend/frontend_build` with one process.
- Scheduler activation is guarded by `AUTO_GENERATION_ENABLED` and a valid
  runtime hostname.
- RSS outbound concurrency is bounded to eight.
- Social SVG composition and browser PNG generation do not persist server files.
- Generated build directories are ignored rather than committed.

### Current evidence

There is no evidence in the repository of an unbounded social-generator cache,
orphaned generated files, duplicate Uvicorn workers or an obvious permanent
object-retention leak. The strongest memory candidates are scheduled transient
peaks: subscriber/analytics list materialization and RSS/article candidate
aggregation. Historical OOMs mean this remains an operational risk, but the
audit cannot attribute any recent Render event without logs and metrics.

### Render log/metrics checklist

For each memory alert or restart, record the exact Europe/London and UTC time,
instance ID, deploy ID and last 100 log lines. Search for:

```text
Out of memory
used over 512MB
OOM
SIGKILL
exit status 137
Killed
MemoryError
Starting scheduler
DailyBrief
WeeklyRoundup
fetch_all_feeds
fetch_category_feeds
daily_article_generation
```

In Render Metrics, capture a 24-hour and seven-day view containing:

- memory used versus 512 MB limit;
- CPU;
- restart count and timestamps;
- request count/latency;
- deploy boundaries.

Distinguish:

- **build failure:** npm/pip/webpack output before Uvicorn startup, no runtime
  request traffic;
- **runtime OOM:** healthy deployment followed by rising service memory,
  termination/restart and fresh Uvicorn startup;
- **expected restart:** deploy/event timestamp aligns exactly and lacks an OOM
  line;
- **application exception:** traceback/failed job without instance termination.

Correlate every runtime OOM with the scheduler table: article generation at
06:00/12:00/18:00, Daily Brief at 07:30 Monday–Saturday, Weekly Roundup Sunday
09:00–12:00. If failures cluster in Weekly Roundup, measure memory before and
after the 15,000-subscriber and 50,000-analytics queries. If they cluster in RSS,
log bounded batch size, feed response bytes and candidate counts without
logging article bodies or secrets.

## Prioritized remediation plan

### Immediate containment

1. Rotate/revoke the exposed Admin credential; confirm old tokens are invalidated
   if the credential/token architecture requires it.
2. Do not run legacy external tests against production.
3. Temporarily treat the branch as stop-ship for further deployment until the
   credential is rotated and the critical test files are sanitized.

### Release-blocking engineering

1. Remove embedded credentials and production mutation defaults from all three
   legacy test modules.
2. Split hermetic and external smoke tests; make the safe full suite deterministic.
3. Restrict CORS to approved origins and add protected-route preflight tests.
4. Repair or remove the three syntactically invalid tracked Python modules.
5. Re-run repository-wide compilation, hermetic backend suite, complete frontend
   suite and production build.

### Next operational hardening

1. Capture Render memory metrics/logs using the checklist before changing
   scheduler/editorial behaviour.
2. Fix header search semantics and no-results feedback.
3. eliminate duplicate runtime head metadata and add server-level Admin noindex.
4. Profile the public article-list endpoint and validate query indexes.
5. Perform one authenticated, non-mutating Admin/social operational walkthrough.

### Maintenance

1. Migrate FastAPI lifecycle handlers and address multipart/gzip warnings.
2. Refresh Browserslist data in a separate dependency-only change.
3. Remove obsolete tracked backups after confirming they are not operational
   recovery artifacts.
4. Correct Threads and deployed-bundle documentation only after this report is
   reviewed.
